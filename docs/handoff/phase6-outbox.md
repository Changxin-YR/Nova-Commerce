### The seam rule, restated

`enqueue` opens no transaction and calls no `commit()`. It appends a row to
whatever transaction the caller already owns, so the event and the business rows
become visible together or not at all. If the caller rolls back, the event was
never queued — which is correct: an event about an order that does not exist is a
lie.

The three call sites stay exactly where the Phase 5 comments put them. Do not
move them, and do not add a pre-check of their own.

## 2. The one design decision that departs from the seam text

The seam comment said the row "must be written with the refund's own idempotency
key". That key **is** stored (`idempotency_key`, indexed with `event_type`), but
it is **not the uniqueness anchor**. The unique is:

```
UNIQUE (event_type, aggregate_type, aggregate_id)
```

Why: an emitter key is only unique *inside its own scope*. An order's
`Idempotency-Key` is unique within `idempotency_records` (a client-supplied string
two users may both send); a refund's is unique per merchant; a payment event's is
unique per provider. A **global** unique on any of those silently drops a
legitimate second event whenever two scopes happen to pick the same string —
and a lost event is invisible (no error, no log, nothing `residue.py` or a
foreign key can see) while a duplicate is loud.

The aggregate triple cannot collide by construction (`aggregate_type` names the
table, `aggregate_id` is its primary key), and "an order is created once" / "a
refund succeeds once" is exactly the set of facts that must not be recorded
twice.

The full argument is in `backend/app/shared/db/models/outbox.py`'s module
docstring. If you disagree with it, **say so explicitly and say what changes** —
do not quietly revert the constraint to the emitter key.

## 3. The teardown obligation (the thing most likely to bite you)

`outbox_messages.merchant_id` is a `RESTRICT` foreign key onto `merchants`, and
`MerchantScopedMixin` gives it a real FK by design. That means **every test
cleanup that deletes a merchant must delete that merchant's outbox rows first**,
or it fails with errno `1451` and stops half-way through an untransactional purge.

This already bit once: the write side landed before the teardown side and
`purge_shop` did not know about the table. Fixed in:

* `backend/tests/integration/commerce/seed.py` → `purge_shop`
* `backend/tests/integration/commerce/residue.py` → `report_residue` (so a leak is
  *visible*: `is_clean` sums `counts`) and `purge_test_residue`
* `backend/tests/integration/{order,payment,fulfillment}/conftest.py`
* `backend/tests/concurrency/test_payment_idempotency.py` (the FG-11 gate has its
  own purge and its own orphan sweep)

`tests/concurrency/test_inventory_oversell.py` deletes a merchant without
touching the outbox. That is safe **and needs to stay true**: FG-09 never runs
`CreateOrderWorkflow`, so it produces no outbox rows. If a future change makes
that suite create orders, that teardown becomes broken.

**If you add a table with a FK onto `merchants`, this obligation arrives with
it.** It is not a one-time fix.

A related pre-existing leak was closed at the same time: `purge_shop` swept
`payment_callbacks` by marker only, so a callback whose event id does not embed
the marker outlived teardown forever (measured: 26 rows accumulating, one per
run). It now also sweeps by `merchant_id`.

   sensitivity. Do not read a green run there as proof the position is irrelevant,
   and do not "simplify" the seam because a mutation survived.

## 7. Traps that cost time in this increment

1. **Encode the line ending on purpose.** `core.autocrlf=true` here, and Python's
   default text-mode write translates `\n` to `\r\n`. A mutation-restore that
   used `write_text()` rewrote two whole files as CRLF (374 spurious bytes) while
   a *text* diff reported **zero differences** — universal-newline handling ate
   the evidence. Use byte reads/writes (`read_bytes()` / `open(p, "wb")`) and
   verify with a byte hash plus `git diff --stat`, not with a text compare.
2. **Some committed files are GBK-mojibake.** `backend/app/modules/order/workflow.py`
   contains 38 occurrences of `搂` (U+6402) where `§` was meant — they are in the
   **committed blob**, not editor damage. A `§`-based search/replace will fail
   against them. Check `git show HEAD:<path> | Format-Hex`-style before assuming a
   tool corrupted anything.
3. **One `nova` schema, no per-process isolation.** Serialise `pytest` runs. Two
   concurrent runs produce failures on rows a fixture *just committed*, and the
   tell is that the failing set moves between runs. (HANDOFF §18.4 item 1.)
4. **`alembic` can be mid-state.** Read `alembic current` before any re-run; a
   reading of "every Phase 5 table MISSING" is usually a downgrade, not a code
   fault (§18.4 item 2).
