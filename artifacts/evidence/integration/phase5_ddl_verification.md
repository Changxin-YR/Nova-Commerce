# Phase 5 DDL verification record (task t1 / T2, data-layer)

Owner: `data-layer`. Revision under test: `3f1ae2c55c54`
(`backend/migrations/versions/20260923_1643_3f1ae2c55c54_phase5_payment_fulfillment_aftersales_and_refund.py`).

This file exists because the design (`docs/architecture/PHASE5_DESIGN.md` section 5)
requires the migration to be **hand-verified in `information_schema`**, and because
`HANDOFF.md` section 6 records that "the migration ran with exit 0" is not evidence of
anything on MySQL - twice over in this phase:

* **Alembic does not autogenerate CHECK-constraint changes on MySQL.** The two new
  caps on the pre-existing `orders` / `order_items` tables appear in *no*
  autogenerated diff at all. Had they been forgotten, `alembic check` would still have
  reported a clean tree while the database had no cap.
* **Reading the constraint names back is not ceremony.** The first application of this
  migration produced `ck_orders_ck_orders_refund_cap` - the naming convention applied
  a second time by `op.create_check_constraint`. The constraint *worked*; it was
  simply named something no `alembic check`, `downgrade` or future migration could
  ever find again. Section 6 records the full defect.

The queries below were run against the live database and the output is pasted
verbatim, not summarised.

Environment: MySQL 8.4.11, `utf8mb4` / `utf8mb4_0900_ai_ci`, `REPEATABLE-READ`,

operand signed is why no `CAST` is needed anywhere in this migration.

### The defect the round trip found

The first version passed the constraint name straight to
`op.create_check_constraint`, which runs it through the metadata naming convention
(`ck_%(table_name)s_%(constraint_name)s`) a second time and produced:

```
orders.ck_orders_ck_orders_refund_cap      :: (`refunded_amount` <= `paid_amount`)
order_items.ck_order_items_ck_order_items_refund_cap :: (`refunded_amount` <= `payable_amount`)
```

`op.drop_constraint` then did the same thing in `downgrade()`, emitting
`ALTER TABLE order_items DROP CHECK ck_order_items_ck_order_items_refund_cap` for a
constraint that does not exist. **The symptom was far worse than the cause**, because
MySQL DDL is non-transactional: the downgrade aborted with errno 3821 *after*
`alembic_version` had already been rolled back to `a7c4e91b2d63`, so every subsequent
`upgrade` was a no-op against a database that still contained the Phase 5 tables. The
schema could never converge, and the failure looked like a phantom - the names in the
database were correct, the names in the source were correct, and only the names being
composed at run time were wrong.

Both call sites now use `op.f(...)`, which marks a name as already final. The emitted
SQL was read back with `alembic downgrade --sql` before re-running it for real:

```
$ alembic downgrade 3f1ae2c55c54:a7c4e91b2d63 --sql
ALTER TABLE order_items DROP CHECK ck_order_items_refund_cap;
ALTER TABLE orders DROP CHECK ck_orders_refund_cap;
DROP TABLE refunds;
DROP TABLE after_sale_items;
DROP TABLE after_sales;
DROP TABLE fulfillment_items;
DROP TABLE fulfillments;
DROP TABLE payment_callbacks;
DROP TABLE payments;
```

## 7. The caps are enforced by MySQL, not by Python (negative controls)

`PHASE5_DESIGN` section 8: "Application checks are not the boundary." Three negative
controls, one per row-level cap.

**How the probe is built, and why it took three attempts.** A cap has to be proved
against real DDL, so the probe needs a table that carries the constraint. Two obvious
constructions silently do **not** work on MySQL 8.4 - both were checked by reading
`TABLE_CONSTRAINTS` back off the twin, which came back with an empty list of
`refund_cap` constraints:

* `CREATE TABLE ... AS SELECT` - copies **no** constraints at all. Re-measured on this
  server: `CREATE TABLE _ascheck AS SELECT * FROM payments WHERE 1=0` leaves **0** rows in
  `TABLE_CONSTRAINTS`. This is the construction the probe below deliberately avoids, and
  the claim holds for it without qualification.
* `CREATE TABLE ... LIKE` - **copies the CHECK constraints, but renames them.** This
  sentence previously said `LIKE` â€œdoes not copyâ€ them, and that was wrong; the verifier
  reproduced the true behaviour: a `LIKE` twin of `orders` carries **7** CHECKs and of
  `payments` **5**, named `_likecheck_chk_1.._N`, with the cap present as
  `_likecheck_chk_6 :: (refunded_amount <= paid_amount)`. The clauses survive; the *names*
  do not. That is why a filter on `constraint_name LIKE '%refund_cap%'` returns nothing off
  a twin and the earlier reading concluded "empty list = not copied".

  The correction matters twice over. First, the rule to record is **never infer the schema
  from a filtered constraint list** - the same mistake the verifier made in the opposite
  direction, briefly believing the caps were missing from the *live* tables for the same
  reason. Second, a `LIKE` twin is **not key-free**: it copies 3 UNIQUE/FK keys on
  `payments` and 2 on `orders`, so a rejection on one has several possible causes and proves
  less than the probe below. That probe is built with `AS SELECT` plus the clause read out
  of `information_schema`, which is strictly the stronger construction - so the negative
  controls' conclusions stand; only the stated reason for avoiding `LIKE` was wrong.

A probe built on either would have inserted cleanly and announced "the cap was NOT
enforced" - a false alarm about a constraint that is perfectly present on the real
table. That is worth recording, because the wrong conclusion is the *plausible* one.

What works, and is also stronger evidence: the check clause is read **out of
`information_schema.CHECK_CONSTRAINTS` for the live table** and attached verbatim to a
twin. Two consequences:

* the `ALTER TABLE ... ADD CONSTRAINT ... CHECK (...)` **succeeding** is itself proof
  that the stored clause is syntactically live on a real table of that shape (a
  malformed or stale clause would be rejected);
* the DDL quoted below is MySQL's own normalised rendering of the constraint, not the
  string this project hoped it wrote.

The twin carries **no foreign keys and no unique keys** (`FK/UNIQUE keys on twin=0`),
so when a violating INSERT is rejected there is nothing else it could have been
rejected for.

```
﻿== the clause MySQL stores (read from information_schema.CHECK_CONSTRAINTS) ==
    payments.ck_payments_refund_cap :: (`refunded_amount` <= `paid_amount`)
    orders.ck_orders_refund_cap :: (`refunded_amount` <= `paid_amount`)
    order_items.ck_order_items_refund_cap :: (`refunded_amount` <= `payable_amount`)

== key-free twins carrying that exact clause ==
    _probe_payments: CHECKs=['ck__probe_payments_refund_cap']  FK/UNIQUE keys on twin=0
    _probe_orders: CHECKs=['ck__probe_orders_refund_cap']  FK/UNIQUE keys on twin=0
    _probe_order_items: CHECKs=['ck__probe_order_items_refund_cap']  FK/UNIQUE keys on twin=0

== CONTROL 1: payments.refunded_amount <= paid_amount ==
    INSERT paid_amount=500, refunded_amount=900 (over the cap by 400)
      -> OperationalError: (pymysql.err.OperationalError) (3819, "Check constraint 'ck__probe_payments_refund_cap' is violated.")

== CONTROL 2: orders.refunded_amount <= paid_amount ==
    INSERT paid_amount=1000, refunded_amount=2000 (over the cap by 1000)
      -> OperationalError: (pymysql.err.OperationalError) (3819, "Check constraint 'ck__probe_orders_refund_cap' is violated.")

== CONTROL 3: order_items.refunded_amount <= payable_amount ==
    INSERT payable_amount=1000, refunded_amount=2000 (over the cap by 1000)
      -> OperationalError: (pymysql.err.OperationalError) (3819, "Check constraint 'ck__probe_order_items_refund_cap' is violated.")

== POSITIVE CONTROL: a legal row must still be accepted ==
    payments paid_amount=500, refunded_amount=500 (exactly at the cap)
      -> *** ACCEPTED ***
    orders paid_amount=1000, refunded_amount=0 (nothing refunded)
      -> *** ACCEPTED ***

== NEGATIVE CONTROL OF THE CONTROL: drop the cap, the same row is accepted ==
    payments refunded_amount=900 with NO cap constraint present
      -> *** ACCEPTED ***
```

Read the results together, because any one of them alone proves less:

1. **Control 1** - `payments.refunded_amount=900` against `paid_amount=500` is refused
   with **errno 3819**. The money record cannot be refunded beyond what was settled.
2. **Control 2** - `orders.refunded_amount=2000` against `paid_amount=1000` is refused
   with **errno 3819**. FG-12 cap 1 at the order boundary.
3. **Control 3** - `order_items.refunded_amount=2000` against `payable_amount=1000` is
   refused with **errno 3819**. FG-12 cap 2, per row.
4. **Positive controls** - the same row shapes *at* the cap (`500/500`, `1000/0`) are
   **accepted**, so the constraint is not simply rejecting everything.
5. **Negative control of the control** - dropping the cap and re-running the exact row
   from control 1 makes it **ACCEPTED**. This is the step that proves the rejection
   came from the cap and not from some incidental column or type mismatch in the probe.

The `REPEATABLE-READ` warning of `HANDOFF.md` section 6 does not apply here: every
result above is the return value of the statement that performed the mutation, on the
same connection that performed it - not a comparison against a snapshot read earlier.

## 8. What this migration did not have to worry about

Before applying the two new caps to the pre-existing tables, the rows were counted,
because a `CHECK` added to a table that already contains violating rows fails - and
MySQL DDL is non-transactional, so a failure partway through an eight-table migration
is a manual recovery:

```
orders rows                                   0
orders NULL amounts                           0
orders VIOLATING cap                          0
order_items rows                              0
items VIOLATING cap                           0
```

The tables are empty on this database, so the caps applied cleanly. On a database with
data the same query set is the pre-flight check: `refunded_amount > paid_amount` cannot
exist under Phase 4 (nothing writes either column before Phase 5), so the expected
answer is always zero, and a non-zero result would mean the caps cannot be added
without first reconciling the offending rows.

## 9. Honest statement of what is *not* proved here

* The probe twins are structurally identical and carry MySQL's own normalised clause,
  but they are **twins**, not the live tables. The live tables carry the same clause -
  that is section 3, read from `information_schema` - and this probe shows the clause
  is enforced when MySQL evaluates it. An `UPDATE` against a live, seeded row is
  exercised by FG-12, which the verifier owns.
* The per-line **cumulative** cap is not verified here at all: it is not a constraint,
  so there is no DDL to read back. `RefundWorkflow` enforces it and FG-12 proves it.
* `alembic check` is clean **as of this revision**. It cannot see CHECK constraints, so
  "No new upgrade operations detected" says nothing about the caps - which is exactly
  why sections 2, 3 and 7 exist.
